Outcomes: the harness handles the loop, you author the rubric

Outcomes is the primitive most architects should commit to first. The mechanics are clean, the lifecycle is well bounded, and the architectural leverage is highest of the four.

Here is what Anthropic actually runs. When you define an outcome, the harness provisions a separate grader in its own context window. The grader has no access to the executor's tools and never sees the agent's reasoning trace. It evaluates the artifact against your rubric and returns a per criterion verdict to the agent. The loop runs until the agent satisfies the rubric, the iteration budget runs out, or the rubric itself fails.

Five terminal states close every outcome: satisfied, needs_revision, max_iterations_reached, failed, interrupted. The default iteration budget is 3, the cap is 20. Pick the budget per task: tight for cheap drafts, generous for hard reasoning.

The marketing says agents self correct against a rubric. The docs add the sharper detail: the grader's reasoning is opaque. You see when it runs and what it decides. You do not see how it reached that decision. The line in the docs is direct: "you see that it's working, not what it's thinking." For audit heavy verticals like finance and healthcare, that opacity is the question to bring to your compliance team before commit.

The other detail the docs surface that the keynote did not: the failed terminal state means the rubric fundamentally does not match the task. Most evaluation systems return a low score when work falls short. Outcomes can return that the rubric itself is not a valid measurement instrument. That is a feedback signal most internal eval pipelines never produce, and it shifts where the engineering effort lives.

How to do it

Anthropic ships the grader. You write the rubric. The rubric is a markdown document, a few dozen lines describing what "done" looks like per criterion. It travels with your codebase like any other versioned artifact.

# API Reference Page Rubric

## Endpoint Coverage
- Every public method in the SDK has a dedicated section
- HTTP method, path, and required headers are documented

## Request Schema
- Every parameter listed with type, required or optional, and constraints
- At least one example value per parameter

## Response Schema
- Success response shape documented with field types
- Each error code (4xx, 5xx) has an example payload and a remediation note

## Examples
- One curl example per endpoint
- One Python SDK example per endpoint, runnable directly

## Output Quality
- Output is one Markdown file per endpoint, in /mnt/session/outputs/
- Internal references use relative links, not absolute URLs

The rubric runs the show. The agent's job is to satisfy it; the grader's job is to check it. Once written, you upload the rubric once and reuse it across sessions.

import anthropic
from pathlib import Path

client = anthropic.Anthropic()

# Upload the rubric once; reuse across sessions
rubric = client.beta.files.upload(file=Path("rubrics/api_reference.md"))

# Spin up a session for one endpoint
session = client.beta.sessions.create(
    agent=agent.id,
    environment_id=environment.id,
    title="API reference: outcomes.define",
)

# Hand the rubric over; the agent starts on receipt
client.beta.sessions.events.send(
    session_id=session.id,
    events=[
        {
            "type": "user.define_outcome",
            "description": "Write the API reference page for outcomes.define",
            "rubric": {"type": "file", "file_id": rubric.id},
            "max_iterations": 5,
        }
    ],
)

Two things to notice. First, rubric accepts a Files API reference, so the same markdown file can drive a thousand sessions. Treat the rubric as a versioned artifact in your repo, not as inline string concatenation. Second, max_iterations defaults to 3 and caps at 20. The iteration budget is a real cost lever; pick it explicitly.

Commit posture

Commit. Outcomes is in public beta with a stable beta header (managed-agents-2026-04-01). The architectural leverage is highest of the four primitives, the lifecycle is fully observable through span.outcome_evaluation_* events, and the only unresolved question is grader opacity for regulated verticals. Dreams: the engine is shipped, the runbook is yours

Dreams is where the keynote framing breaks down most clearly. The blog post calls it "a scheduled process that reviews your agent sessions and memory stores." The docs call it an asynchronous job. The difference is not cosmetic.

Here is what Anthropic actually runs. You hand dreams.create an input memory store, a list of up to 100 sessions, a model (claude-opus-4-7 or claude-sonnet-4-6), and an instructions field of up to 4096 characters. The platform spins up a worker that reads the input store and the sessions, extracts patterns, and writes a fresh memory store. The job moves through four states: pending, running, completed, failed, or canceled. The dream itself runs as a session, so you can stream its events through the same observability surface you already use for agents.

Two mechanics matter. First, the input store is never modified. The dream produces a new store; you choose whether to attach it to future sessions or discard it. Second, there is no platform schedule. The platform does not run dreams on a cadence. You build the cron, you write the policy that decides when to dream, and you own the queue.

How to do it

Trigger a dream when there is enough new session history to make compaction worthwhile. The simplest pattern is a nightly job in your existing scheduler.

import anthropic

client = anthropic.Anthropic()

# Pull the last 100 sessions from your tracking system
recent_sessions = list_recent_sessions(limit=100)

# Create the dream
dream = client.beta.dreams.create(
    memory_store_id=current_store.id,
    session_ids=[s.id for s in recent_sessions],
    model="claude-opus-4-7",
    instructions=(
        "Focus on coding style preferences and tool patterns. "
        "Ignore one off debugging notes."
    ),
)

Two design choices live in this call. The instructions field shapes what gets curated. "Focus on coding style preferences and tool patterns; ignore one off debugging notes" produces a different output store than "Capture every workflow the agent converged on." The choice is editorial. It belongs in your codebase, not in operator memory.

Memory mutation under Dreams is git shaped. Each call produces a new store with a fresh ID. Stores accumulate; lineage matters. Rolling back means attaching an older store ID to your live agent.

import time

# Poll for completion
while True:
    dream = client.beta.dreams.retrieve(dream.id)
    if dream.status in ("completed", "failed", "canceled"):
        break
    time.sleep(30)

# Review the new store before adopting
if dream.status == "completed":
    if review_passes(dream.output_memory_store_id):
        # Attach the new store; future sessions inherit it
        client.beta.agents.update(
            agent_id=agent.id,
            memory_store_id=dream.output_memory_store_id,
        )
    else:
        # Discard. The previous store stays attached.
        pass

Two more notes. The cost scales roughly linearly with input session length, so start small and instrument before scaling. And the manual review path (read the new store, attach only after a human signs off) is the production path for regulated verticals. The auto adoption path is research grade and worth waiting on.

Commit posture

Hybrid. Commit to the manual review path now: trigger dreams, review outputs in the Console, attach when satisfied. Defer auto adoption until the research preview matures. The split is real and the docs make it possible without forcing the auto path.

Multi-Agent: the orchestration is platform side, the topology is yours

Multi-Agent Orchestration is the primitive with the heaviest mechanics in the May 6 release. It is also the primitive where the keynote framing diverges most from the API reality.

Here is the first thing the docs make explicit and the keynote did not. Multi-Agent supports exactly one level of delegation. A coordinator can call workers; workers cannot call workers of their own. The blog reads as if you are getting recursive agent decomposition. The API reality is coordinator plus flat workers, full stop. If your task tree is hierarchical (research a topic, draft an outline, write each section, review each section, where every step decomposes further), you flatten it before committing or you chain via Outcomes.

The second mechanic with architectural weight is shared state. The docs say specialists "work in parallel on a shared filesystem." Read further and the truth is sharper: every agent in a Multi-Agent session runs in the same container. Same kernel, same process namespace, same network. The only thing isolated between agents is conversation context.

Treat them as cooperating threads on shared mutable state. Standard concurrency patterns apply: file locking for contended writes, atomic moves where order matters, dedicated working directories per agent for ephemeral output, named queues for handoff. Engineers from a microservices background that assume isolation will write code that races. They will not get told they are racing; the platform does not flag concurrent file mutations.

One more discrepancy to note. The blog labels Multi-Agent as public beta. The docs page header labels it research preview. Verify before signing off on production. Beta and research preview imply different SLAs, change windows, and supportability. The bundle hides the gradient.

How to do it

Multi-Agent topologies are static. You declare the coordinator's callable agents at orchestrator setup, and the coordinator can only delegate to that pre declared set. There is no runtime agent discovery.

import anthropic

client = anthropic.Anthropic()

# Create the specialists first
researcher = client.beta.agents.create(
    name="Researcher",
    model="claude-sonnet-4-6",
    system_prompt="You research a topic and return a brief.",
)
drafter = client.beta.agents.create(
    name="Drafter",
    model="claude-opus-4-7",
    system_prompt="You draft sections from a brief.",
)
editor = client.beta.agents.create(
    name="Editor",
    model="claude-opus-4-7",
    system_prompt="You edit drafts against a style guide.",
)

# Declare the team at orchestrator creation
orchestrator = client.beta.agents.create(
    name="Drafting coordinator",
    model="claude-opus-4-7",
    callable_agents=[researcher.id, drafter.id, editor.id],
    system_prompt=(
        "Delegate research to the researcher, drafting to the drafter, "
        "editing to the editor. Synthesize into a final article."
    ),
)

The coordinator delegates by sending messages to threads belonging to those agents. Threads are persistent within the session, so the coordinator can follow up later and the worker retains context.

# Run a session with the coordinator
session = client.beta.sessions.create(
    agent=orchestrator.id,
    environment_id=env.id,
)

client.beta.sessions.events.send(
    session_id=session.id,
    events=[{
        "type": "user.message",
        "content": "Draft an article on the May 6 Managed Agents release.",
    }],
)

# Coordinator decides which workers to call.
# Each worker runs in its own thread, on the shared container.
# Outputs land at /mnt/session/outputs/<worker_id>/ by your convention.

Two engineering notes. First, design your worker outputs to land in dedicated subdirectories under /mnt/session/outputs/<worker_id>/. The container is shared; convention is your only conflict resolver. Second, capture the per worker thread events to your observability stack as soon as the session ends. The Console traces are good for debugging individual sessions, but production diagnosis needs your own observability surface.

Commit posture

Selective. Commit for flat coordinator plus workers patterns where the workers are genuinely independent. Defer for hierarchical task decomposition until Anthropic ships nesting. Verify the public beta versus research preview status against your support contract before any production rollout.

Webhooks: the smallest section, the lifecycle's connective tissue

Webhooks is the lightest of the four primitives, and the easiest to underestimate. The mechanics are simple, but webhooks are what make the platform feel composable: define an outcome, run an agent, get notified when done, fan out to your own systems.

Here is what Anthropic ships. HTTPS POST to your URL, HMAC signature in the headers, retries on 5xx, at least once delivery. Standard webhook infrastructure. The events you can subscribe to map to the session lifecycle: session start and end, outcome evaluation start and end, dream completion, session interruption.

The marketing reads as if subscribing to webhooks gets you most of the way to event driven integration. The docs surface the work the marketing skips. You build the endpoint. You verify the HMAC signature. You handle idempotency on the at least once delivery semantics. You map event types to actions in your own systems.

The architectural rule is simple: every event type you subscribe to needs a deliberate downstream action. If an event arrives and your handler has no opinion about what should happen next, do not subscribe. Noise drowns signal, and webhook stream debt accumulates.

How to do it

Run a small handler. Verify the signature, check idempotency, dispatch on event type.

from fastapi import FastAPI, Request, HTTPException
import hmac, hashlib, os

app = FastAPI()
SECRET = os.environ["ANTHROPIC_WEBHOOK_SECRET"].encode()
seen_event_ids = set()  # In production: Redis or your DB

@app.post("/anthropic/webhook")
async def handle(request: Request):
    body = await request.body()
    sig = request.headers.get("anthropic-signature", "")
    expected = hmac.new(SECRET, body, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(sig, expected):
        raise HTTPException(403)

    payload = await request.json()
    if payload["id"] in seen_event_ids:
        return {"status": "duplicate"}
    seen_event_ids.add(payload["id"])

    if payload["type"] == "outcome_evaluation.end":
        record_outcome_to_audit_log(payload)
    elif payload["type"] == "dream.completed":
        open_review_ticket(payload)
    return {"status": "ok"}

Commit posture

Commit. Webhooks is public beta with standard webhook patterns. The smallest mechanical surface of the four. Treat it as plumbing and move on.

What this means for the next managed primitive

The pattern repeats across all four primitives. Anthropic ships the harness; you ship the rubric, the runbook, the topology, the subscriber. The keynote framing compresses the developer's responsibility into a sentence ("self improving agents," "specialists work in parallel," "scheduled curation"). The docs restore the responsibility into something specific you can plan around.

Four questions earn you a clean read of the next managed primitive Anthropic announces. What is the lifecycle, named in states with terminal conditions? What is the SLA gradient, and which features in the bundle are research preview versus public beta versus GA? What shared resources does the primitive expose, and where do my concurrency assumptions break? What is the audit surface, and what is opaque?

The piece is opinionated about Outcomes, Dreams, Multi-Agent, and Webhooks because the docs are now explicit about what they are. The diligence pattern is portable to whatever ships next. The keynote will sell abstraction; the docs will reveal a harness. Reading the docs is the new architectural literacy.
